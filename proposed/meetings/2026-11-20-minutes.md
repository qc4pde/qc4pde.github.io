## Software & Tooling

* Scope (Andy): shared tooling for metadata capture; a results catalog that tracks results where they live rather than in a mono-repo; keeping published codes current with evolving SDKs (LLM-assisted, in a structured way); a solver framework modeled on petsc4py with swappable components (e.g. state preparation); interoperable backends, including HPC integration
* Supports the data and infrastructure; does not own the data (that sits with Benchmarking & Stewardship)
* Status: existing Q8020-CFD org has a dozen or more repos with published codes (GE, ORNL, RPI, others) being kept current; these can be linked or rebranded under the broader PDE umbrella
* metautil: captures metadata from open-box codes via the harness, or harvests it with LLMs from closed-box output
* Next steps: tidy and release assets before advertising them; coordinate with Brightskies on a larger shared component library; possible educational uses
* OpenQSE (Amir Shehata and others) is interested in an applications component or working group in their ecosystem; agreed to start the conversation now rather than wait

## Benchmarking & Stewardship

* Main deliverable to aim for: a paper defining a list of benchmarks and standards for how to benchmark them (metrics, resources, problem size), how scaling relates to algorithm and hardware timelines, and how results are cataloged and compared rigorously
* Owns the data: what is tracked and why, and how researchers should format results and metadata so they fit the shared body of results
* Expand the sample benchmark set beyond fluids: solid mechanics, fusion, bio, finance
* Scope covers applications and algorithms (the overall PDE-solving ecosystem, including hybrid), not applications alone
    + Map which algorithms suit which applications, select test cases, then hand pipelines to Software & Tooling
* Uncertainty quantification (Melvina):
    + Results vary run to run even for one case; need a rule for what to report without cherry-picking
    + Proposal: a UQ stage every benchmark passes through to score performance across backends and over time (e.g. hardware drift)
    + Envisioned as a pip-installable quantum-UQ library (working name pronounced "cookie")
    + Applies to both benchmarking guidance and tooling support
    + Andy: add UQ next to the L2 metric on the benchmarks page; detailed design to happen in a separate conversation
